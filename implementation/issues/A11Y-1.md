# A11Y-1 — Dark mode from the device setting, WCAG 2.1 AA in both schemes

- **Status:** Implemented (Wave 16, uncommitted at time of writing; no independent review yet).
- **Priority:** medium
- **Guarantee:** A player whose device is set to dark mode gets a dark app, without doing anything. Both schemes meet WCAG 2.1 AA — resting state, hover state and visibility — and the suite fails if either stops meeting it.

## Origin

User request: detect the device setting and follow it, then, separately: "Make it ADA compliant, all of the site (dark and light mode)." The second half changed the work. A dark theme that merely looks right is easy; one that is provably readable is a different job, and it turned the task into an audit.

## What made it tractable

The app already ran on 12 colour tokens in `:root`, so dark mode is a second set of values rather than a second set of rules. Everything that bypassed a token had to be found first — that was most of the work.

## What was found

| Found | Consequence if left |
|---|---|
| `--color-success` used as `var(--color-success, #2e7d32)` and **never defined** | Always silently used the fallback. Invisible because a fallback looks deliberate. |
| `--color-surface-muted` used with an `rgba(0,0,0,0.03)` fallback and **never defined** | A black tint, which on a dark surface disappears entirely. |
| `background: white` in five places (four panels on My Topics, plus the Account toggle knob) | **This is what broke My Topics in dark mode**: light text on a hard-coded white panel. A hex-only audit missed it; the word "white" is not a hex code. |
| Twelve hard-coded colours across eight files, mostly `#ffffff` labels on accent/danger fills | Dark mode inverts those fills, so a white label on a light fill fails contrast. |
| Hover contrast never checked in dark mode | `a11y-audit.js` exists *because* axe never hovers, but it only ran in the default scheme. |
| `/topics` and `/notifications` had no axe coverage at all, in either scheme | Two whole pages unchecked. |

## What was done

- **Palette**: a `@media (prefers-color-scheme: dark)` block redefining the tokens, plus `color-scheme: light dark` on `html` so the browser themes what CSS does not — form controls, scrollbars, spellcheck underlines, and the pre-paint background flash. No toggle: the browser already knows the person's system choice, and a toggle needs its own storage plus a control in a header that is already tight on a phone.
- **New tokens**: `--color-on-accent` / `--color-on-danger` (text *on* a filled control, which has to invert with the fill), `--color-success`, `--color-surface-muted`, and warning/info chip pairs. Every hard-coded colour in the app now resolves to a token; the only survivors are the video letterbox (`#000`) and the toggle knob, both annotated.
- **Contrast chosen by measurement, not eye.** Every pair was computed against WCAG 2.1 AA before it was written, and the ratio is recorded in the CSS next to the value that earned it. The dark pairs land between 6.7:1 and 17.3:1 against a 4.5:1 requirement.
- **Enforcement**: `accessibility.spec.js`, `visibility.spec.js` and `modals.spec.js` now run in **both** schemes via `test.use({ colorScheme })`. That covers axe resting state, the bespoke hover-contrast audit and the invisible-control audit, over every page and nine modal states.

## Not covered, deliberately

- **`:focus-visible` is not audited per-control** the way hover is. The shared outline rule uses `--color-accent` (5.6:1 light, 7.7:1 dark), so it is fine today, but nothing would catch a component overriding it. Keyboard users depend on this; it is the most valuable next step.
- **`:active` states** are unchecked. Brief, but real.
- **Disabled controls** are exempt from contrast requirements, so they are correctly ignored.
- **Automated checks are not a compliance certificate.** axe catches contrast, names, roles and structure. It cannot judge whether focus order makes sense, whether an error message is useful, or whether a screen reader announces a round changing. A manual audit with an actual screen reader is the honest next step if compliance matters legally.

## Affected surface

| Area | Change |
|---|---|
| `src/index.css` | Dark token block, new tokens, `color-scheme: light dark` |
| `src/App.css`, `src/pages/{Dashboard,ThemeIdeas,GroupView,Account,Login}.css`, `src/components/{ProfileSetupModal,YouTubeSearch}.css` | Hard-coded colours replaced with tokens |
| `e2e/accessibility.spec.js` | Both schemes; `/topics` and `/notifications` added |
| `e2e/visibility.spec.js`, `e2e/modals.spec.js` | Both schemes, so the hover audit covers dark |

## Done when

- A device set to dark renders the app dark, with no user action and no flash of light.
- axe reports no violations on every covered page and modal, in both schemes.
- The hover audit passes in both schemes.
- No colour in the app bypasses a token except the two annotated cases.
- Full suite green.

## Depends on

None. `UX-1` and `NT-1` supplied components this had to keep readable.
